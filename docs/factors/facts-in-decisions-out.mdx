<GovernanceFactor title="Facts In, Decisions Out" number={5}>

<Principle>
Governance decisions should be computed from structured requests and return explicit results.
</Principle>

<Problem>

Without a visible decision boundary and a defined request shape, governance
becomes a vague mixture of scripts, tickets and human memory. Hidden chains and
UI-only toggles cannot explain why they permitted or denied—or what obligations
followed.

</Problem>

<PositiveExamples>

<RevealItem title="“May this agent call this tool on this dataset?”">
A concrete question with principal, action, resource and context—answerable by an engine.
</RevealItem>

<RevealItem title="“May this branch be promoted?”">
A promotion decision that should return permit/deny, reasons and any obligations.
</RevealItem>

<RevealItem title="“May this app raise this intent with this context?”">
An inter-app request with an explicit shape and an inspectable result.
</RevealItem>

<RevealItem title="“Permit with obligations: encrypt, notify, record.”">
A decision that is more than a boolean—obligations travel with the permit.
</RevealItem>

</PositiveExamples>

<NegativeExamples>

<RevealItem title="Hidden script chains">
Outcomes produced by opaque automation with no request/response boundary.
</RevealItem>

<RevealItem title="Approval by tribal knowledge">
Decisions that live only in people’s heads and cannot be audited or reused.
</RevealItem>

<RevealItem title="UI-only toggles with no decision record">
State changes that look like policy but leave no facts, reasons or evidence.
</RevealItem>

<RevealItem title="Policies that cannot explain why they denied">
Opaque deny/allow with no rationale, obligations or inspectable inputs.
</RevealItem>

</NegativeExamples>

<Tools>

- Cedar
- OPA
- XACML
- DMN
- Gatekeeper
- App directories and typed intents

</Tools>

<AntiPatterns>

- Policy as workflow
- Assumptions instead of facts
- Allow/deny with no rationale

</AntiPatterns>

<Discussion>

The strongest lineage behind this factor runs through policy and decision
engines. XACML formalised request/response evaluation and obligations; Cedar
defines principals, resources, actions and optional context in schema; OPA
accepts structured input and can return arbitrary structured output; DMN
provides a business-readable format for explicit decision logic. These systems
differ in style, but they agree on the important thing: the decision boundary
must be visible and the request must have a defined shape.

That makes this factor easy to explain in plain language. Governance should
answer concrete questions with concrete answers. It should be possible to
inspect what facts were considered, which policy logic applied, what result was
produced, and what obligations or remediation followed. Without that boundary,
governance becomes a vague mixture of scripts, tickets and human memory.

</Discussion>
