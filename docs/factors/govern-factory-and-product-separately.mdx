<GovernanceFactor title="Govern the Factory and the Product Separately" number={4}>

<Principle>
The system you run and the system that produces it are different sensitive activities.
</Principle>

<Problem>

Collapsing build-time and run-time into one governance object produces misleading
status. A green product score can hide a compromised pipeline; release provenance
mixed into end-user access controls obscures which domain failed.

</Problem>

<PositiveExamples>

<RevealItem title="A build twin with provenance, branch protection and signing status">
Shows factory integrity on its own terms: how artefacts were produced and gated.
</RevealItem>

<RevealItem title="A run-time twin with authorisation posture and incident history">
Shows product governance: what the running system may do and how it has behaved.
</RevealItem>

<RevealItem title="Separate policies for AI model training pipelines and production inference endpoints">
Keeps training-factory risk distinct from inference-product risk.
</RevealItem>

<RevealItem title="Distinct governance for desktop app distribution and desktop app context sharing">
Treats shipping the app and sharing context as different sensitive-activity domains.
</RevealItem>

</PositiveExamples>

<NegativeExamples>

<RevealItem title="One “green” score for an app whose build pipeline is compromised">
A single badge that hides factory failure behind product status.
</RevealItem>

<RevealItem title="Release provenance mixed into end-user access controls">
Collapses two domains so neither set of evidence or owners stays clear.
</RevealItem>

<RevealItem title="Treating CI/CD and production as one blob">
Erases the boundary between how software is made and what it may do when running.
</RevealItem>

</NegativeExamples>

<Tools>

- SLSA
- in-toto
- CycloneDX
- OPA / Gatekeeper
- Kubernetes

</Tools>

<AntiPatterns>

- Pipeline blindness
- Provenance as a run-time property
- App-level dashboards that hide build risk

</AntiPatterns>

<Diagram>

The factory that produces artefacts and the product that runs them are connected, but separately twinned.

```mermaid
flowchart LR
Source --> BuildFactory
BuildFactory --> Artifact
Artifact --> RuntimeProduct
BuildFactory --> FactoryTwin
RuntimeProduct --> ProductTwin
```

</Diagram>

<Discussion>

Supply-chain standards make this distinction unavoidable. SLSA provenance and
in-toto link metadata describe how artefacts were produced, by which authorised
actors, through which steps. That is governance of the factory. By contrast,
run-time governance tools such as OPA and Gatekeeper
govern what a running system may do with data, peers and users. The build
pipeline and the deployed service are connected, but they are not the same
governance object.

For Ten Factor Governance, this distinction is a gift because it produces a vivid story.
The product can be green while the factory is red; the desktop app can be
approved to share context while the release pipeline that shipped it is missing
provenance; the agent can be tightly sandboxed while its model-training pipeline
remains opaque. Separate twins make those facts visible instead of collapsing
them into a single misleading status badge.

</Discussion>
